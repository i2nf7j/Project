## 1. 범위와 역할

이번 작업은 UX 설계와 지정 스택의 기술 검토다. 제품 코드, 실행 환경 설치, DB 생성, 배포는 포함하지 않는다.

| 역할 | 담당 산출물 | 책임 |
|---|---|---|
| Planner | 이 문서, product.md·WORKFLOW.md 진행 상태 | 요구사항 대조, 의견 조율, 다음 단계 지정 |
| Designer | [ux-spec.md](design/ux-spec.md) | 역할별 흐름, 화면 목록, 텍스트 와이어프레임, 상태별 UX |
| Developer | [technical-plan.md](development/technical-plan.md) | 환경 조사, 공식 기술 근거, 구현 구조·제약과 향후 검증 계획 |

2026-09-09 파일 조사에서 src는 비어 있고 package.json·Gradle 빌드 파일은 발견되지 않았다. IDE에 표시된 이전 파일명이 실제 파일의 존재를 의미하지 않으므로 디스크에 있는 Designer.md·Developer.md를 사용한다. 이전 한도 중단 시 UX 초안은 저장되었으나 기술 검토 문서는 저장되지 않았다. 이번 재위임도 실행 대기에 머물러 중단하고 Planner가 Developer 지침에 따라 기술 검토를 직접 완료했다. Designer 에이전트는 최신 메뉴에 맞춰 UX와 역할 지침을 수정했다.

## 3. 공통 설계 기준

다음은 확정된 기능을 구현 가능한 화면·기술 동작으로 연결하는 Planner의 설계 기준이다. 사용자 미정 권한이나 기능 범위를 확대하는 결정은 아니다.

1. UI는 서버가 허용한 조작을 표시하고, 서버는 조작 시 권한과 현재 상태를 다시 검사한다. 화면 버튼 숨김만으로 권한을 구현하지 않는다.
2. 조회 데이터와 편집 중 입력을 분리한다. 자동 갱신이 입력을 덮지 않으며 버전 충돌은 새 값 확인 후 다시 저장하게 한다.
3. 업로드는 검증 미리보기와 실제 적용 결과를 구분한다. 정상 28행은 반영하고 오류 2행은 보존하되, 저장 실패까지 성공으로 표시하지 않는다.
4. 공조 수락은 작업 생성과 함께 일관되게 처리한다. 변경 저장 성공 후 알림·갱신을 전달한다.
5. 미처리 공조에 대한 종결 제한과 거절·철회 권한은 product.md의 설계 기본안이다. 이를 사용자 확정사항으로 표기하지 않는다.
6. 보고값은 값과 기준시각을 함께 보관한다. 서버 중단으로 16시 자료가 없으면 현재 값을 소급하여 표시하지 않는다.
7. 수동 건수의 실제 상세 작업 중복은 개별 정보 없이 완전히 자동 판별할 수 없다. 출처 연결·분리 표시·입력 안내로 관리한다.
8. 전시기 가독성은 텍스트 와이어프레임만으로 검증 완료할 수 없다. 다음 UI 단계에서 목표 화면 크기의 시안과 이후 실제 브라우저로 확인한다.

발견한 차이와 조정:

- UX 문서가 존재하지 않는 technical-review.md를 참조했다. 실제 산출물명 technical-plan.md로 수정했다.
- UX 구현 순서에서 공조가 별도 단계로 읽힐 수 있었다. 첫 상세 설계 범위에 공조를 포함하고, 기본 흐름 뒤에 연결하는 것은 코드 작성 순서임을 명시했다.
- 식별번호를 찾을 수 없는 업로드 행에 ‘기존 값 유지’라고 쓰면 해당 인원이 등록되어 있다고 오해할 수 있어 ‘적용 안 함’으로 수정했다. 기존 인원 오류 행의 값 보존 규칙은 유지한다.

일반 사용자·정비사의 부대 운영정보 조회, 공조 거절·철회와 미처리 요청의 종결 제한, 시연 단계 목록 등은 두 문서에서 계속 제안·미정으로 둔다. 이번 검토가 그 권한을 자동 승인하지 않는다. 정비부서의 자기 부서 현황 대시보드와 운영정보 조회 권한은 구분한다.

### 5.1. 검토 중 받은 메뉴 개정 지시

- 2026-09-09 최신 지시로 두 탭 제약을 해제하고 대시보드·정보통신 운영·부대운영·정비관리 순서를 적용한다.
- 최초 요청은 BNOC가 접수·배정하고 정비부서는 배정 작업을 확인한다. 기존 정비사의 최초 접수 승인과 혼동하지 않는다. 공조의 수신 정비반 직접 수락은 유지한다.
- 정비 진행의 목록·캘린더는 같은 작업 데이터를 사용한다. 월간·날짜별 정비 현황은 분석·조회 화면으로 분리하고 대시보드와 집계 기준을 공유한다.
- 부서별 ‘접수 건’은 요청과 혼동되지 않도록 ‘배정 작업’ 표시를 제안한다. 작업 중·미완료·조치 완료·종결 대기를 같은 단위의 상호 배타적 상태로 오해하지 않게 한다.
- 사용자 메시지 링크의 C:/Users/User/Project/PROPOSAL.md는 금융관리 기획서였다. 실제 열린 파일과 요청 내용에 부합하는 현재 저장소 PROPOSAL.md에 반영했으며 금융 문서는 수정하지 않았다.

## 7. 기술 검토와 UX 조율 결과

후속 사용자 답변 반영: 요청서 1건과 수량 메모, 확인·시작 분리와 보류, BNOC 재배정, 같은 대대 타 부서 정비 요약 조회, 당월 완료 실적 기준을 확정했다. 병력 와이어프레임은 부서 블록 내 세로 목록으로 변경하고 근무자(야간)에 구역·직책별 가상 계급·성명·전화번호를 추가했다. 약 75인치 TV·Edge를 대상 환경으로 기록했으며 픽셀 해상도는 미정이다. 다음에는 대표 시나리오·입력항목을 먼저 검토하고 물리 DB·API 확정은 그 뒤에 진행한다.

PHASE-02의 문서 검토를 완료했다. 실제 구현 준비 완료를 의미하지 않는다. 기술 근거와 원문 링크는 [technical-plan.md](development/technical-plan.md)에 기록했다.

| 쟁점 | UX 요구 | 기술 검토 결과·Planner 정리 |
|---|---|---|
| 버전 조합 | 요청한 화면·동작 유지 | 지정 스택 유지, Gradle 8.6 첫 검증 후보. Boot의 기본 Kotlin과 지정 2.0.21 차이를 실제 의존성·JSON·프록시 검증 항목으로 지정 |

| 공조·종결 | 수신 부서 수락 후 BNOC 반영 | 최초 요청은 BNOC 배정, 공조만 수신 수락. 작업 확인 여부와 상태를 분리하고 중복 수락 방지 |

확정 범위를 바꿔야 할 기술적 근거는 이번 문헌 검토만으로 확인되지 않았다. 상세 UI와 API·데이터 설계는 진행할 수 있으며, 제품 구현 단계의 첫 작업에는 지정 조합의 최소 빌드·기동 검증을 포함해야 한다.

다음 요청 예시:

> Planner가 최신 product.md, ux-spec.md, technical-plan.md를 기준으로 Designer의 UI 상세 명세와 Developer의 첫 기능 데이터·API·검증 계획을 조율해줘. 네 상위 메뉴와 BNOC 접수·정비부서 진행 흐름을 유지하고, 제품 코드는 아직 구현하지 마.
