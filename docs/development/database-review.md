## 권장안: 단일 DB, 업무별 테이블

요청 → 접수 → 진행 → 종결은 하나의 업무 생명주기다. 페이지별 DB 대신 하나의 MySQL DB에서 같은 접수 ID와 작업 ID를 참조한다. 아래는 구축 전 제안이며 실제 DB 생성·연결은 수행하지 않았다.

| 데이터 | 책임 |
|---|---|
| 비행단·부서·사용자 접근 범위 | 조직 관계와 서버 조회·수정 권한 |
| 사전 등록 계정 | 2026-10-06 확정: 관리자가 사용자·소속·역할·조회 범위를 준비. 사용자 ID와 역할을 분리하고 요청 소유자·알림 읽음·개인 설정·변경 이력을 사용자 ID에 연결. 계정·권한 신청/승인 데이터는 첫 시연에서 제외 |
| 접수 | 최초 요청, 접수 승인, 최종 종결; 페이지 이동 시 복사하지 않음 |
| 부서 작업 | 접수에 연결된 주관·공조 작업, 배정·진행·완료 |
| 작업 이력 | 상태·부서 변경 시각과 변경자, 기간 말 기준 집계 |
| 공조 요청 | 대기·수락·거절·철회 상태, 생성 작업의 고유 연결, 요청 사유와 별도인 처리 사유·처리자·시각 |
| 수동 집계 | 상세 미등록 건수의 출처와 이월 연결. 16시 보고 원본 테이블·스케줄러는 제외 |

접수 한 건에 여러 부서 작업이 연결될 수 있다. 요청 건수와 부서 작업 건수를 구분하며, 조치 완료와 BNOC 종결도 구분한다. 통계 페이지용 원본을 따로 복제하지 않는다. 규모가 커지면 측정 후 집계 테이블·읽기 복제본을 검토하며 복제 지연을 표시한다. 부대별 망 분리나 독립 운영 요구가 생기면 물리 분리를 재검토한다.

## 실시간 조회와 정합성

일반 SELECT는 데이터를 수정하지 않는다. InnoDB 일관 읽기는 스냅샷을 사용하므로 조회와 쓰기가 함께 가능하다. 다만 서로 다른 API·트랜잭션으로 읽은 수치와 목록은 시점이 달라 불일치할 수 있다. 요약·그래프·목록을 동일 필터와 짧은 REPEATABLE READ 읽기 트랜잭션으로 생성하고 조회 기준 시각을 함께 반환하는 방식을 제안한다. SSE 연결 동안 DB 트랜잭션을 열어 두지 않는다.

- 접수 승인·작업 생성·이력 저장은 한 트랜잭션에서 처리한다. 재전송 식별자와 고유 제약으로 중복 생성을 방지한다.
- 작업 수정은 버전 조건으로 덮어쓰기를 방지한다. 종결·작업 추가·공조 수락·거절·철회는 같은 접수 행을 일관된 순서로 잠그고 조건을 재검사한다. 대기 상태의 공조에만 조건부 갱신을 허용하고 처리 사유·인증된 사용자·시각을 남긴다. 종결 시 관련 작업 전체 완료와 대기 공조 없음 조건을 재검사해 종결 직후 작업 추가 및 수락·거절·철회 경합을 막는다. 이는 서버 구현 기준이며 현재 목업에서 DB 경합을 검증한 것은 아니다.
- 커밋 이후에만 SSE 갱신 신호를 전송한다. 재연결·알림 누락 시 전체 재조회와 주기적 보정 조회로 복구한다.
- 비행단 전환 시 이전 요청을 취소하거나 응답 번호를 검사해 늦게 도착한 다른 비행단 결과가 화면을 덮지 않도록 한다.
- 서버에서 허용 비행단·부서 범위를 검증하고 SSE에도 같은 범위를 적용한다. 상위 조회 API는 수정 권한을 갖지 않는다.
- 비행단·부서·상태·기간 조회 조건에 맞는 인덱스와 실행계획을 확인하고 상세는 페이지 처리한다. 집계 조인으로 작업이 중복되지 않게 작업 ID 기준으로 계산한다.

공식 근거: [MySQL 8.0 일관 읽기](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-consistent-read.html). 위 운영 방식은 이 기능을 바탕으로 한 프로젝트 설계 제안이다.

## 이번 화면 변경과 검증 범위

상위 조회자의 비행단 선택 화면에 BNOC와 같은 완료·미완료 누적 막대그래프, 부서 선택, 작업 내역을 추가한다. 기존 가상 집계 자료를 고유 ID가 있는 가상 작업으로 구성하여 그래프·목록이 같은 원본을 사용한다. 과거 기간에는 종료일 이후 완료 내용이 표시되지 않는다. 기존 BNOC 편집 화면 접근은 허용하지 않는다.

현재 상위 조회 자료는 BNOC localStorage 자료와 별개인 고정 시연 데이터다. 실제 비행단 서버·DB·실시간 통합은 미구현이므로 DB 동시성이나 부하 안전성을 검증했다고 볼 수 없다. 구축 후 동시 접수·공조 수락·완료와 종결 경합, 여러 조회자 갱신, SSE 단절 복구, 비행단 전환 응답 역전, 권한 외 조회 차단을 통합 검증해야 한다.

검증 결과: `node --test tests/viewer.test.cjs tests/maintenance.test.cjs` 14건 통과. `PLAYWRIGHT_CHANNEL=msedge`로 상위 조회 브라우저 테스트 통과(전체 비교, 부서 작업 선택, 기간 집계, 읽기 전용, 역할 복귀, 390px 모바일). Playwright 기본 Chromium 바이너리가 없어 설치된 Edge로 검증했다.
