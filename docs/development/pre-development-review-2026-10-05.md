# 개발 착수 전 종합 검토 — 2026-10-05

## 판단

**기반 구축과 첫 업무 흐름 개발은 조건부 착수 가능하다. 전체 화면을 한꺼번에 제품으로 옮길 준비는 아직 끝나지 않았다.** 핵심 정비 흐름과 운영 일정·장비 연결을 시연하는 목업은 마련되어 있지만, 최신 업무 규칙의 단일 기준, 실제 사용자·조직 식별, 상세 데이터/API 계약, 재현 가능한 빌드·테스트 환경을 먼저 맞춰야 한다.

이번 검토는 분석·검증이다. 제품 코드나 업무 규칙은 변경하지 않았다. 목업의 브라우저 저장과 역할 선택 기능을 실제 인증·DB·다중 사용자 동기화로 평가하지 않았다. 기존 사용자 변경사항을 유지했다.

검토 자료: PROPOSAL.md, WORKFLOW.md, product.md, ux-spec.md, technical-plan.md, database-review.md, design-development-review.md, 목업 README/UI-REVIEW, 핵심 업무 모델·UI·테스트. 활성 design-taste-frontend 스킬은 랜딩·포트폴리오용이며 데이터 중심 업무 UI를 적용 대상에서 제외하므로 이 프로젝트의 미관 기준으로 적용하지 않았다.

## 1. 우선 해결할 발견 사항

### 후속 해결 기록

- 1단계 사용자 답변: 현재 목업의 병력 규칙으로 통일하기로 확정(2026-10-05).
- 반영: product.md §4에 직접 지정 > 자동 오프 > 기본 주간, 기간 경계·겹침, 근무 편성 연계, 확인 무효화와 업로드 원본 보존 기준을 통합했다. 기획·UX·기술·DB·진행 문서와 목업 안내를 맞췄다.
- 기존 확정 범위도 본문에 반영했다: 16시 보고 제외·날짜별/기간별 엑셀 유지, PC 1280px·전시기 지원, BNOC·관리자 대리 접수 및 병력 조회 권한. product.md의 계획정비 신규 집계 시점도 기존 확정인 등록·배정일로 맞췄다.
- R-01은 일부 해결이다. 상위 조회 설명 등 남은 문서 정합성과 R-02~06의 모델·UI·테스트 수정은 후속 단계다. 아래 발견 사항은 최초 검토 당시의 근거로 유지한다.
- 1단계 검증: `node --test tests/operations.test.cjs tests/staffing.test.cjs` 10건 통과. 확인한 과거 병력·16시 보고 충돌 문구를 현재 기준 문서에서 정리했다. 제품 코드 변경과 서버 검증은 수행하지 않았다.
- 2단계: 사용자 선택에 따라 R-02를 목업에서 해결했다. 같은 대대 부서별 비교표와 수치 전용 summarizeDepartments를 추가했고, 기존 상세용 summarize는 자기 부서 제한을 유지한다. 과거의 타 부서 필터 테스트는 상세 권한 유지 테스트로 의미를 명확히 하고 별도 비교 요약·상세 차단 테스트를 추가했다. 모델 16건과 두 진입점의 비교표 브라우저 검증을 통과했다. 서버의 다부대 권한 검증은 아직 미실시다.

P1은 관련 기능을 실제 구현하기 전에 규칙·동작을 맞춰야 하는 항목, P2는 구현 명세 확정 및 해당 화면 마무리 전에 해결할 항목이다.

### R-01 · P1 · 개발 기준 문서가 최신 목업과 서로 다르다

- 10월 3일 확정사항에서는 16시 보고를 제외했지만 product.md §6.4, technical-plan.md §6, database-review.md의 데이터 책임, ux-spec.md의 수용 기준은 계속 이를 요구한다.
- product.md에는 일반 사용자의 운영 조회가 미정이고 대리 접수도 후속 검토로 남아 있다. 최신 WORKFLOW에는 병력 조회 제한, BNOC 대리 접수, 알림 대상, 일정·작업 연결이 확정되어 있다.
- 병력은 product.md에서 당일 값이 없으면 미입력, 주간·야간 독립이다. 반면 목업 README의 10월 1일 설명과 operations-model.js:25는 기본 주간·예외 기간·야간 근무 다음 날 자동 오프를 사용한다. 미입력으로 되돌릴 문제가 아니라 **최신 동작을 개발 문서에도 반영할 문제**다.
- 운영 계획정비는 최신 UI-REVIEW에서 등록·배정일부터 신규 집계한다. product.md §6.4에는 미래 예정일부터 포함하는 이전 제안이 남아 있다.
- 상위 조회 상세 공개와 제17비행단 공유 여부도 product.md 및 database-review.md의 과거 설명과 최신 목업이 다르다.

영향: 화면, API, 통계, 테스트를 서로 다른 규칙으로 구현할 수 있다.

보완: product.md를 현재 기준으로 정리하고, UX·기술 문서가 이를 참조하도록 한다. 이전 결정은 이력으로 분리한다. 기능별로 `확정 / 제안 / 미정 / 목업 구현 / 서버 미구현`을 표시한다. 단순히 문서 끝에 우선 적용 문구를 계속 추가하는 방식은 피한다.

### R-03 · P1 · 미처리 공조를 끝낼 예외 경로가 없다

close()는 모든 작업이 완료되어도 대기 공조가 있으면 종결을 거부한다. 현재 모델은 공조 요청·수락만 제공하고 거절·철회는 제공하지 않는다. 잘못 보낸 공조나 지원 불필요 상황에서는 수락해 작업을 만든 뒤 완료하는 우회가 필요해진다.

재현: R-DEMO-003의 기존 작업을 모두 완료한 뒤 BNOC 종결을 호출하면 대기 공조 때문에 거부된다. 목록의 requestStatus는 전체 작업 완료만 보고 종결 대기로 표시할 수 있어 목록과 상세 버튼의 조건도 다르다.

보완 제안: 수신 부서 거절, 요청 부서 철회, 사유·처리자·시각 기록을 정한다. 대기 공조가 있을 때에는 종결 불가 이유를 목록·상세에서 동일하게 표시한다. BNOC 강제 철회 권한은 자동 추가하지 않는다. 거절·철회 권한은 기존 문서에서도 제안 상태이므로 확정 기록이 필요하다.

근거: [공조·종결 모델](../design/mockup/maintenance-model.js), [요청 상태·종결 화면](../design/mockup/maintenance-ui.js), product.md §6.2.

### R-04 · P1 · 완료 처리 경로에 따라 알림 결과가 다르다

workflow-improvements.js의 M.updateTask 래퍼는 완료 시 BNOC 알림을 만든다. 그러나 운영 일정의 완료 처리는 linkOperationWork()에서 작업의 completed와 history를 직접 바꾸므로 이 경로를 거치지 않는다.

재현: 새 계획정비 생성 → 운영 일정에서 완료 처리. 연결 작업 완료일은 입력되지만 해당 작업의 BNOC 완료 알림 증가량은 0이다. 기존 workflow 테스트는 주로 정비 작업에서 완료하는 경로를 검증하므로 이 차이를 놓친다.

보완: 정비 진행·운영 일정 어느 화면에서 완료해도 같은 업무 서비스가 완료 조건·이력·알림을 처리하게 한다. 요청 재시도에도 완료 알림이 중복되지 않아야 한다. 두 진입점의 완료 테스트를 함께 둔다.

근거: [일정·작업 연결 코드](../design/mockup/workflow-improvements.js), [업무 브라우저 테스트](../../tests/workflow.browser.cjs).

### R-05 · P2 · 대리 접수 제목 미리보기가 다른 부서를 표시한다

maintenance-ui.js:93의 input 처리에서 requester를 항상 `가상 A부서`로 덮어쓴다. 처음 렌더링과 실제 createRequest()는 대리 접수 입력값을 사용하므로 미리보기와 저장 결과가 어긋난다.

재현: BNOC 대리 접수에서 요청 부서 REVIEW DEPT, 대상 REVIEW ASSET 입력 → 미리보기는 `[가상 A부서] REVIEW ASSET 점검 요청`.

보완: 일반 사용자는 인증된 계정의 부서, 대리 접수는 허용된 실제 요청 부서를 사용한다. 입력 중·제출 후·조회·엑셀에서 같은 제목을 검증한다. 실제 접수 계정과 요청자를 별도 식별자로 저장한다.

근거: [제목 미리보기](../design/mockup/maintenance-ui.js), [요청 저장](../design/mockup/maintenance-model.js).

### R-06 · P1 · 회귀 테스트 기준과 실행 환경을 정리해야 한다

- 모델 실행 결과: Node 테스트 러너 집계 **42건 중 41 통과, 1 실패**.
- system-operations.test.cjs:3은 구성 11개, 최상위 net을 기대하지만 최신 계층은 기반통신체계를 추가하여 12개, 최상위 infrastructure다. 첫 assert에서 중단하므로 그 파일의 이후 검증은 실행되지 않았다.
- 같은 파일에는 net이 최상위라는 전제의 필터·이동 검사도 남아 있다. 숫자 하나만 변경해서 해결했다고 판단하면 안 된다.
- 일부 브라우저 테스트는 `.tmp-off-tools/node_modules/playwright`, 일부는 `require('playwright')`를 사용한다. 기본 실행에서는 모듈을 찾지 못했고 기존 임시 의존성 경로를 NODE_PATH로 지정한 뒤 실행됐다.
- 제품 package.json, lockfile, Gradle Wrapper·빌드 파일, DB migration, ui-spec.md, implementation-plan.md는 조사한 제품 경로에 없다. src에는 파일이 없다.

보완: 테스트 의존성과 실행 명령을 저장소에 고정하고, 새 체크아웃에서 동일하게 실행하게 한다. 테스트에 쓰는 시연 데이터 기준도 함께 버전 관리한다. 여러 최신 모듈·테스트가 Git 미추적 상태이므로 개발 기준 커밋을 만들기 전에 포함 대상과 tmp·캡처·임시 의존성 제외 대상을 정한다. 기존 사용자 변경을 이 검토에서 커밋하거나 정리하지 않았다.

## 2. 실제 개발 전에 정할 계약

다음은 목업 자체의 보안 취약점 판정이 아니라 서버 구현에 필요한 설계 조건이다.

| 영역 | 현재 상태·위험 | 착수 전에 구체화할 내용 |
|---|---|---|
| 계정·조직·권한 | 역할이 사실상 시연 계정 ID다. 요청 owner, 알림 readBy, 개인 설정이 user/network/bnoc 같은 역할에 연결된다 | userId·wingId·squadronId·departmentId·역할·특기를 분리. 같은 역할 2명과 다른 부대 같은 역할의 접근 테스트. CPCON은 역할 외 특기 조건 유지 |
| 권한 신청·관리 | 개인 설정 안내는 있지만 신청·승인 기능은 미연결. 승인 주체도 WORKFLOW에서 대기 상태 | 첫 시연은 관리자 사전 계정 등록으로 가능한지, 권한 신청 UI가 제출 필수인지 정한다. 임의로 승인 권한을 부여하지 않는다 |
| 장비·공문 접근 | 타 부서 편집 범위가 UX 문서에 미정 | 목록·상세·등록·수정·삭제·공문 재사용·원본 다운로드·원본 삭제별 범위를 정한다. 여러 부서가 공유하는 공문의 삭제 권한과 영향도 함께 정한다 |
| DB 모델 | 단일 DB·업무별 테이블 방향은 있으나 물리 스키마는 없다 | 조직·계정·권한, 요청·작업·공조·이력, 운영 구성·일정·장비, 공문·장비 연결, 병력 기간·확인·근무 편성, 지시·알림 수신/읽음을 식별자로 연결 |
| 일정·작업 관계 | 화면에서 양방향 값을 수정하고 일부 경로는 직접 상태 변경 | 일정↔작업의 연결 수, 완료의 주체, 날짜 변경·취소·연결 해제 규칙. 자동 생성 계획정비 취소와 기존 접수의 영향 일정 취소를 구분 |
| 장비 식별·보존 | 같은 모델 여러 대를 등록할 수 있고 연결된 원장은 삭제를 막는다 | 내부 불변 ID와 관리번호·제조번호 분리, 관리번호 유일성 범위, 이동·운영 종료·폐기 구분, 공문 원본과 연결 관계의 삭제 정책 |
| API | 기술 방향만 있고 실행 가능한 계약이 없다 | 경로·요청/응답·필수값·허용 enum·페이지 처리·권한 범위·오류 코드·현재 버전. 화면이 사용할 allowedActions와 종결 불가 사유 등 정의 |
| 변경 충돌 | 목업은 한 브라우저 객체를 수정한다 | version 기반 충돌 응답, 재시도 식별자, 접수 배정·공조 수락 고유 제약. 종결과 공조 수락/추가의 경합을 동일 접수 기준으로 제어 |

## 4. 화면·프런트엔드 전달 보완

- 실제 파일로 확인한 진입점은 mockup.html과 mockup-responsive-motion.html이다. IDE 탭의 mockup-clean-institutional.html은 현재 docs/design 목록에 없다. 구현할 시안의 경로와 기준 버전, 공유 모듈 범위를 ui-spec.md에 한 번 명시한다.
- PC 최소 1280px와 전시기 범위를 유지한다. 모바일 지원은 추가하지 않는다. 기본 시안의 전시기는 기존 테스트에서 1366×768·1920×1080을 확인했지만 실제 약 75인치 TV의 해상도·배율·시청 거리는 아직 별도 확인 대상이다.
- 새로운 시안은 1280px 진입 시 문서 전체 가로 넘침과 pageerror가 없음을 확인했다. 모든 화면·모든 역할·전시기 자동 순환을 새 시안에서 회귀 검증한 것은 아니다.
- 시안에 있는 간격·타이포·상태색·표·필터·다이얼로그·오류·빈 결과를 공통 컴포넌트 명세로 옮긴다. 목업의 전역 render와 M/SO 함수 재정의 체인을 React에 그대로 이식하지 않는다. R-04처럼 진입점마다 업무 처리가 달라질 수 있다.

- 전시기에는 데이터 최종 갱신 시각과 단절/오래된 자료 표시가 필요하다. 시안의 12초 일정 순환·일시정지·감소된 모션 설정을 유지하고 실제 표시 장치에서 읽을 수 있는지 확인한다.
- 과거 날짜 엑셀의 운영 상태·조직 명단이 현재값이라는 현재 안내를 유지한다. 과거 이력을 재현하는 통계와 현재 원장을 같은 의미로 표시하지 않는다.

## 5. 기술·배포 준비

이번 환경 조사에서는 node·git이 PATH에서 확인됐다. java·javac·gradle·pnpm·mysql은 확인되지 않았다. PC에 미설치되었다는 뜻은 아니며 DB 서비스나 외부 개발 환경도 조사하지 않았다.

첫 구현 작업에 다음 최소 실행 검증을 포함한다.

1. 지정 Java 17·Kotlin 2.0.21·Boot 2.7.18과 Gradle Wrapper로 컴파일·기동. JSON null/default·프록시 및 실제 Kotlin 의존성 버전 확인.
2. MySQL 연결·한글·시간대·초기 migration·고유키·롤백 검증.
3. React 19·TypeScript strict·Vite의 타입 검사와 production build, pnpm 및 의존성 버전 고정.
4. 목표 WAR 실행 방식에서 SPA 새로고침·컨텍스트 경로·API·세션 쿠키·CSRF·SSE 재연결 검증.
5. 가상 사용자 seed, 새 DB 초기화, 업무 자료 및 첨부 백업·복원, 재배포·되돌리기 절차 작성. 시연 전 복구를 실제로 한 번 실행.

지정 스택을 이 검토에서 변경하지 않는다. 다만 Boot 2.7.18은 2.x OSS 지원 종료 릴리스라는 점을 공식 자료에서 재확인했다. 인터넷 시연 환경의 유지보수·패치 책임과 실제 운영 전환 계획을 정해야 한다. [Spring 공식 릴리스 안내](https://spring.io/blog/2023/11/23/spring-boot-2-7-18-available-now/).

기존 Gradle 후보와 WAR 구성은 여전히 실행 검증 대상이다. 지원 범위가 겹친다는 문헌 근거를 빌드 성공으로 바꾸어 기록하지 않는다. [Kotlin Gradle 호환 문서](https://kotlinlang.org/docs/gradle-configure-project.html), [Boot 2.7.18 배포 문서](https://docs.spring.io/spring-boot/docs/2.7.18/reference/htmlsingle/#howto.traditional-deployment).
