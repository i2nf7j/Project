                                # 프로젝트 단계와 요청 가이드

## 현재 판단

PROPOSAL.md를 바탕으로 Planner에게 PM·시스템 분석을 맡기는 것은 현재 단계에 적절하다. 기획서만으로 전체 구현을 지시하기보다 업무 규칙과 권한을 분석하고 화면·기술 설계를 맞춘 후 기능별로 구현한다. 모든 문서를 완벽히 끝낼 때까지 기다릴 필요는 없으며 준비된 기능부터 진행한다.

역할 문서는 자동 실행 파일이 아니다. 요청에 [Planner](Planner.md), [Designer](design/UI/Designer.md), [Developer](development/Developer.md)를 명시하여 역할을 적용한다. 병렬 에이전트가 필요하면 구체적인 독립 작업과 함께 명시한다.

## 단계별 요청

### 1. 요구사항·업무 분석 — 1차 작성 완료

산출물: [product.md](product.md). 완료 조건은 요구사항·권한·업무 흐름·개념 데이터·수용 기준을 연결하고 미정 사항의 영향을 구분하는 것이다.

확정한 사항: 네 상위 메뉴, BNOC 최초 접수·배정과 정비부서 작업 확인, BNOC·관리자 대리 접수, 공조 수신 직접 수락, 진행 내 일정 통합, 추가 조치 제외, 기간 중복 제거·날짜별/기간별 엑셀, 포함 정상 행 우선 적용. 16시 보고 보관은 제외한다. 병력은 직접 지정 > 자동 오프 > 기본 주간 기준이며 PC 최소 1280px와 전시기만 지원한다. 상세 개발 기준은 product.md를 따른다.

남은 분석이 필요한 경우의 요청 예시:

> docs/Planner.md 역할로 docs/product.md의 남은 취소·정정 규칙과 시연 데이터를 검토해줘. 이미 확정한 공조·업로드·통계 기준은 유지하고 추가 조치 절차는 도입하지 마. 필요한 결정만 예시와 권장안으로 정리해줘.

### 2. UX 설계와 기술 가능성 검토 — 문서 검토 완료

산출물: docs/design/ux-spec.md, docs/development/technical-plan.md. 완료 조건은 역할별 핵심 흐름과 필요한 화면 상태가 정의되고, 지정 스택의 확인 결과·제약·미검증 항목이 구분되는 것이다.

2026-09-09 최신 메뉴를 반영하고 문서 검토를 완료했다. [조율 결과](design-development-review.md)에서 실제 환경 확인과 미실시 테스트를 구분했다. 다음은 3단계이며 코드 구현·설치는 아직 수행하지 않았다.

요청 예시:

> Planner가 Designer와 Developer의 검토를 조율해줘. Designer는 product.md를 바탕으로 메뉴, 역할별 사용자 흐름, 병력 카드·고장접수·정비작업의 와이어프레임과 오류 상태를 ux-spec.md에 작성해줘. Developer는 현재 코드와 지정 스택·WAR·MySQL·실시간 갱신의 구현 가능성을 technical-plan.md에 정리해줘. Planner는 충돌과 미정 사항을 product.md에 반영해줘. 이 단계는 검토와 설계만 수행해줘.

독립적인 UX 분석과 기술 검토는 함께 진행할 수 있다. 한 사람이 여러 AI 역할을 순서대로 수행해도 된다.

### 3. UI 및 첫 기능의 상세 설계

후속 진행 순서 조정: 먼저 대표 업무 시나리오와 화면 입력항목을 검토한다. 사용자 요청에 따라 물리 DB·API를 곧바로 확정하지 않는다. 네트워크체계팀의 랜선 고장·모니터 정비·PC 포맷, BNOC 재배정, 부서별 병력 세로 목록, 근무자(야간) 연락처 표시 사례를 사용한다.

산출물: docs/design/ui-spec.md, docs/development/implementation-plan.md. 완료 조건은 화면·데이터·상태·권한·API·검증 기준이 서로 맞는 것이다.

요청 예시:

> Planner 주관으로 첫 시연 흐름의 상세 설계를 진행해줘. Designer는 ux-spec.md를 바탕으로 공통 스타일·컴포넌트·PC 및 전시기 UI 명세를 작성해줘. Developer는 로그인부터 접수·배정·조치 완료·BNOC 종결까지 데이터 모델, API 계약, 상태 전이와 테스트 계획을 작성해줘. Planner는 의견을 조율하고 파일별 담당과 수용 기준이 있는 구현 작업 목록을 만들어줘.

### 4. 첫 사용자 흐름 구현

완료 조건은 가상 계정으로 신청부터 종결까지 실제 저장·권한·화면 갱신이 연결되는 것이다. 정적 화면만 완성된 경우 별도로 표시한다.

요청 예시:

> Planner가 확정된 첫 구현 작업을 Developer에게 지시하고 완료까지 조율해줘. 시연 계정 로그인, 미지정 고장 신청, BNOC 배정, 정비사 조치 완료, BNOC 종결, 두 브라우저 자동 갱신을 구현해줘. Designer는 구현 화면을 검토하고 Developer는 빌드·권한·상태 전이·동기화를 검증해줘. 미구현·모의 처리·검증 불가 사항은 명확히 보고해줘.

### 5. 나머지 기능 확장

정비 핵심 흐름 후 병력·근무자(야간), 운영상태·상황·지시, 집계·일정·전시기를 기능 단위로 완성한다. 각 기능의 분석·디자인·구현·검증을 반복한다.

요청 예시:

> Planner가 현재 완료 근거와 product.md를 비교해 다음 기능 묶음을 선정하고 구현까지 조율해줘. 해당 기능의 미정 규칙을 먼저 정리하고 Designer의 화면 검토와 Developer의 구현·검증을 포함해 완료해줘. 기존 기능의 회귀와 부대별 권한도 확인해줘.

### 6. 통합 검증과 제출 준비

산출물: docs/validation.md, docs/demo-guide.md. 완료 조건은 실제 실행 결과, 남은 결함, 시연 계정·가상 데이터 준비, 재실행·배포 방법이 확인되는 것이다.

요청 예시:

> Planner 주관으로 PROPOSAL.md와 product.md의 수용 기준을 실제 구현과 대조해줘. Developer는 통합 테스트·빌드·시연 환경을 검증하고 Designer는 전시기 가독성과 역할별 조작을 확인해줘. 발견한 결함을 수정하고, 검증 근거와 남은 제한을 validation.md에, 11월 6일 제출용 시연 순서와 실행 방법을 demo-guide.md에 작성해줘.

## 요청 구성 원칙

요청에는 담당 역할, 입력 문서, 대상 기능, 원하는 산출물, 구현 허용 범위, 완료 기준을 포함한다. 단계별 명령은 사용자가 구분해서 진행하고 싶을 때의 예시이며 매 단계마다 별도 승인을 의무화하는 절차는 아니다.

```text
[역할]로 [기준 문서]를 읽고 [기능·단계]를 수행해줘.
[산출물·수정 경로]에 반영하고 [검증 기준]까지 확인해줘.
확정사항은 유지하고 미정사항은 제안과 확정을 구분해줘.
이번 작업은 [분석만 / 설계까지 / 구현·검증까지] 진행해줘.
```

## 목업 검토 후 확정 사항 (2026-10-03)

이 절은 앞선 모바일 지원·독립 시연 자료·미연동·결정 대기 설명보다 우선한다. 적용 대상은 docs/design/mockup.html 통합 목업이며 서버 구현 완료를 뜻하지 않는다.

- 일반 사용자는 병력 메뉴·조회·병력 엑셀 시트를 사용할 수 없고 근무자(야간)는 조회·내보내기 가능하다. 정비사는 부대 전체 병력을 조회하며 수정은 BNOC·관리자 권한이다.
- 장비 운영 명칭은 장비 관리로 변경했다. PC 최소 1280px와 전시기만 지원하며 모바일 화면 및 모바일 수용 조건은 제외한다.
- BNOC·관리자의 대리 접수를 추가했다. 실제 요청 부서와 접수 계정을 구분한다. 16시 보고 보관 기능과 준비 중 버튼은 제외하고 날짜별·기간별 엑셀만 유지한다.
- 정비사는 미확인 배정·공조·오늘 작업·보류 작업을, 일반 사용자는 내 요청·근무자·담당 부서를 먼저 본다. 엑셀 도구와 CPCON 전체 설명은 펼쳐서 사용한다.
- 새 운영 정비 일정은 담당 부서의 계획정비 작업을 생성하거나 기존 작업 하나에 연결한다. 작업 완료는 일정에 반영되며 양쪽 상세에서 이동할 수 있다. 기존 요청에 연결한 영향 일정의 취소는 원래 정비 요청을 취소하지 않는다. 자동 생성된 계획정비 작업만 일정 취소에 따라 집계에서 제외한다.
- 운영 구성의 장비는 장비 관리의 등록 자료를 연결한다. 기존 가상 구성 장비는 최초 실행 시 장비 목록으로 이관한다. 구성에서 삭제해도 장비 관리 원장은 유지하며 정비 기록이 있는 구성은 운영 종료로 보존한다.
- 제17비행단의 상위 조회 화면과 엑셀은 동일 브라우저에 저장한 BNOC 자료를 참조한다. 가상 비행단 A·B는 독립 예시 자료다. 여러 사용자·PC 사이의 동기화는 서버 구현 범위다.
- 신규 요청은 BNOC, 배정·재배정은 담당 부서, 공조 요청은 수신 부서, 작업 완료는 BNOC 알림으로 연결한다. 알림 읽음은 작업 확인과 별개다. 개인 정비사 지정은 현재 부서 단위 배정 범위를 확장하지 않는다.
- 지시사항은 제목·본문 직접 입력 및 게시 전 검토 방식이다. 자동 문서 분석이나 자동 요약으로 표시하지 않는다. 실제 날짜와 가상 업무 기준일을 구분하고 미등록 과거 근무 편성을 임의로 만들지 않는다.

검증: 관련 모델 테스트 36건, workflow.browser.cjs(권한·대리 접수·일정 연결·취소 분리·상위 조회·장비 참조), experience.browser.cjs(알림·읽음·테마·PC/전시기), export.browser.cjs(실제 XLSX 다운로드·기간·시트·권한), system-operations.browser.cjs(구성·이동·삭제·일정·저장 유지)를 통과했다.

### 후속 마무리 검증 (2026-10-03)

운영 구성의 장비 상세 링크는 장비 목록 탭으로 이동하고 부서·망 필터를 초기화한 뒤 해당 장비명으로 검색한다. 직접 입력 게시물의 원문 다운로드 표기를 수정했다. GPS 지점명이 PC 최소 폭에서 겹치지 않도록 보정했다. 기존 모바일 브라우저 검증 조건은 PC 1280px 이상으로 교체했다. 추가로 accounts, gps, instructions, viewer, maintenance 브라우저 검증과 workflow, system-operations 회귀 검증을 통과했다.

### 현재 계정 표시·개인 설정·추이 수치표 (2026-10-03)

현재 로그인 계정의 비행단·대대·부서, 계급·이름·역할을 별도 상단 영역에 표시한다. 조회 대상 비행단과 계정 소속을 구분하며 상위 조회자는 상급부대 가상 계정으로 표시한다. 이름과 조직은 시연 자료다. 개인 설정에서 업무 연락처를 계정별로 저장하고 테마는 기존 브라우저 설정을 사용한다. 이름·계급·소속·권한은 직접 수정하지 않는다. 권한 신청의 승인 주체는 사용자 답변 대기이며 신청·승인 기능은 아직 추가하지 않았다.

정비현황 추이 수치표는 기간을 열로, 신규 배정·조치 완료를 행으로 배치한다. 좌우 버튼·스크롤·키보드로 이동하고 구분 열은 고정한다. account-settings.browser.cjs와 experience.browser.cjs로 계정 표시·저장 유지·설정 격리·가로표·PC 폭·전시기를 확인했다.

### 새 시안 디자인 범위 (2026-10-05)

사용자 확정: mockup-responsive-motion.html은 PC 최소 1280px와 전시기만 대상으로 한다. 앞으로 모바일 메뉴·반응형·모바일 검증 제안은 제외한다. 원본 mockup.html과 공통 모듈은 이번 시안 변경에 포함하지 않는다. 체계 정비 일정은 화면 높이에 맞춰 페이지를 나누고 12초마다 자동 전환하며 전체 건수·현재 범위를 표시한다.

### 개발 전 보완 1 — 병력 규칙·기존 확정 범위 정리 (2026-10-05)

사용자 확인에 따라 병력의 직접 지정 상태 > 당직·야간 다음 날 자동 오프 > 기본 주간을 개발 기준으로 확정했다. 날짜별 확인 완료는 별도로 관리하고 관련 자료 변경 시 해제한다. 기간 겹침·종료·근무 편성 변경·명단 연결·업로드 누락 보존 기준은 [product.md §4](product.md#4-업무-흐름과-상태)에 통합했다.

PROPOSAL·UX·기술·DB 문서에 같은 기준을 반영하고 16시 보고 제외, PC·전시기만 지원, BNOC·관리자 대리 접수와 기존 병력 조회 권한을 정리했다. 과거 조율 기록은 당시 이력으로 표시했다. 이번 단계는 문서 수정이며 목업 동작 변경이나 서버 구현 완료를 의미하지 않는다.

다음 보완은 같은 대대 타 부서 정비 요약의 표시 범위를 확인한 뒤 모델·UI·테스트를 맞추는 것이다. 공조 거절·철회와 취소·정정 권한은 별도 질문으로 순차 확정한다.
