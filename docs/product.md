## 1. 현재 단계와 범위

요구사항 분석 후 UX 설계·기술 검토 단계의 기준 문서다. 문서 작성은 구현 완료를 의미하지 않는다. 2026-09-09 읽기 전용 파일 조사에서 src는 비어 있고 package.json과 Gradle 빌드 파일이 발견되지 않았다. 실행 가능한 제품이나 빌드 결과는 아직 없다.

목표는 3명이 2026-11-06까지 제출할 인터넷 환경의 웹 시연 체계다. 2026-09-09 개정에 따라 상위 메뉴는 대시보드·정보통신 운영·부대운영·정비관리로 구성한다. 독립된 부대별 권한, 가상 자료, 지정 스택을 유지한다. 별도 설치형 앱, 외부 군수체계 연동, 제품 AI 기능은 제외한다. 향후 인트라넷 운영과 이번 시연 배포를 구분한다.

아래 구현 순서는 우선순위 제안이며 기능 축소 합의가 아니다.

## 4. 업무 흐름과 상태

### 정비

일반 사용자가 정비 요청에서 희망 부서를 선택할 수 있다. BNOC는 정비 접수에서 희망 부서 유무와 관계없이 접수·배정을 확정한다. 정비부서는 정비 진행에서 배정 작업을 확인하고 동일 화면의 목록·캘린더로 관리한다. 부서별 작업은 원격·출동 조치, 일반·긴급 우선순위, 일정과 진행상태를 가진다. 모든 관련 작업이 조치 완료되면 BNOC 확인 후 종결한다.

| 대상 | 상태 전이 기본안 | 주체·조건 |
|---|---|---|
| 접수 | 신청 → 접수 승인·배정 | BNOC, 중복 접수·배정 방지 |
| 작업 확인 | 미확인 → 확인 | 배정된 정비부서, 확인 시각 기록. 작업 상태와 별도 속성 |
| 접수 | 접수 승인 → 조치 중 | 관련 작업 시작 시 반영하는 방식 제안 |
| 작업 | 작업 예정 → 작업 중 → 조치 완료 | 담당 정비반, 완료 조치내용 기록 |
| 작업 | 작업 중 ↔ 보류 | 정비반, 보류 사유 기록 |
| 접수 | 조치 중 → 종결 대기 | 관련 작업 전체 조치 완료 |
| 접수 | 종결 대기 → 종결 | BNOC 확인 |

반려·취소 권한, 배정 전 선조치, 작업이 없는 접수의 처리, 협조 부서 추가 후 상태 계산은 상세 결정 대상이다. 정비사의 조치 완료 건수와 BNOC 종결 건수는 혼합하지 않는다.

### 병력 및 업로드

기준 인원 명단과 기준일별 상태를 구분한다. BNOC가 파일을 업로드하면 행별 오류와 변경 예정 값을 확인한 뒤 정상 행부터 적용한다. 누락·오류 행의 당일 값은 보존한다. 인원 행에서 직접 수정한 내용도 이력을 남긴다. 당일 상태가 없으면 미입력으로 표시하며 전날 값을 자동 복사하지 않는다. 확정한 처리 기준은 §6.5~6.6에 따른다.

### 야간 근무와 동기화

각 대대 BNOC가 자기 대대 근무표를 관리한다. 근무자 소속이 다른 부대여도 관리 대대 권한으로 등록하며 다른 부대의 원본 근무표를 수정하지 않는다. 통합 조회는 허용된 대대 자료를 취합한다. 주간 상태와 야간 근무는 독립이다. 자동 갱신 후에도 편집 중인 입력은 보존해야 한다.

### 6.2. 공조 요청·수락

- 같은 대대의 정비반이 다른 정비반에 공조를 요청한다. 요청받은 정비반의 권한 있는 담당자가 직접 수락한다.
- 요청·수락 결과를 BNOC에도 알리고 현황에 반영한다. BNOC 사전 승인 대기 단계는 두지 않는다.
- 수락 전 요청은 작업 건수에 포함하지 않는다. 수락하면 같은 접수에 협조 부서 작업을 연결하여 1건 추가한다.
- 동일 요청을 동시에 수락하거나 재전송해도 협조 작업이 중복 생성되지 않도록 한다.
- 각 부서는 자기 작업을 수정·완료한다. 공조 수락 권한이 다른 부서의 작업 수정 권한을 의미하지 않는다.
- 최초 정비 요청의 BNOC 접수·배정과 공조의 수신 부서 직접 수락을 구분한다. 정비사의 최초 요청 승인 권한은 2026-09-09 개정으로 배정 작업 확인으로 바뀌었다. 긴급 선조치는 유지한다.

예: A반이 B반에 전원 점검을 요청하면 접수 1건·작업 1건이다. B반 수락 후 접수 1건·작업 2건이 되고 BNOC 화면에 표시된다. BNOC 승인 버튼을 누를 필요는 없다.

세부 설계 기본안: 미처리 공조 요청이 있으면 종결을 보류하고 요청 수락·거절·철회 여부를 먼저 정리한다. 거절은 수신 부서, 철회는 요청 부서가 사유와 함께 처리하는 방식을 제안한다. BNOC의 강제 철회 등 추가 권한은 자동 도입하지 않는다.

### 6.3. 조치 완료·종결의 단순화

현재 흐름은 신청, 승인·배정, 작업 수행, 정비반 조치 완료, BNOC 종결이다. BNOC의 추가 조치 요청 버튼, 완료 작업 재개, 재완료 횟수·재개 유입 통계는 이번 범위에서 제외한다. 일부 부서만 완료한 경우에는 나머지 부서 작업이 끝날 때까지 종결 대기 조건을 충족하지 않는다.

예: 작업 3건 중 2건 완료이면 미완료 1건을 계속 관리한다. 3건 모두 완료한 뒤 BNOC가 종결한다. 별도의 반송·재작업 단계를 거치지 않는다.

새 장애는 기존 일반 고장 신청 기능으로 등록할 수 있다. 이전 접수 연결이나 종결 취소 전용 기능은 이번 결정으로 추가하지 않는다. 오입력 정정·작업 취소의 세부 권한은 별도 미정이며, 추가 조치 절차 제외를 기록 수정 전체 금지로 해석하지 않는다.

### 6.4. 기간별 통계와 16시 보고

기간별 관리대상은 기간 시작 시 미완료인 작업과 기간 중 새로 대상에 포함된 작업을 합쳐 같은 작업 ID를 한 번만 집계한다. 일별 대상 합계를 주간·월간 대상으로 사용하지 않는다. 기간 내 같은 부서 작업이 여러 날 이월되어도 한 번만 센다. 접수 건수와 부서별 작업 건수는 별도다.

완료는 관리대상 중 기준 시점에 조치 완료인 작업 수이며, BNOC 종결 수와 구분한다. 미완료는 유효 대상에서 완료를 뺀 값이고 보류도 미완료에 포함한다. 진척도는 완료/유효 대상이며 대상 0건은 ‘—’다. 취소는 기획서대로 대상에서 제외하되 취소·정정의 세부 규칙은 별도 결정한다.

예: 월요일 대상 10건 중 6건 완료. 화요일 4건 이월에 신규 2건을 추가하고 3건 완료. 화요일 현황은 대상 6건·완료 3건·미완료 3건·50%이고, 화요일 기준 주간은 대상 12건·완료 9건·미완료 3건·75%다. 일별 대상의 합인 16건으로 표시하지 않는다.

16:00에 당시 일일 현황을 보관하고 현재 현황은 계속 갱신한다. 16시 6/10건 완료 후 16:30에 2건을 더 완료하면 보고 기록은 6/10, 현재 현황은 8/10이다. 보고 기록은 이후 작업 변경으로 덮어쓰지 않는다.

설계 기준: 시간대는 Asia/Seoul을 사용한다. 종료된 기간은 기간 말 상태, 진행 중인 기간은 현재 상태로 집계한다. 미래 예정 작업은 예정 기간부터 포함하되 조기 착수 시 실제 착수일부터 포함하는 방식을 제안한다. 16시에 서버가 꺼져 있어 기록이 없으면 ‘미생성’으로 표시하며 현재 값을 과거 16시 값으로 위장하지 않는다. 보고 정정·복원과 08:30 별도 기록은 아직 확정하지 않는다.

수동 건수는 등록 묶음과 이월 출처를 연결하여 매일 신규 건수로 다시 더하지 않는다. 신규·완료·취소·잔량을 분리하고 완료·취소 합이 대상을 넘지 않도록 검증한다. 개별 정보가 없는 수동 건수와 상세 작업 사이의 실제 중복을 자동으로 완전히 판별할 수 없으므로 입력 안내와 분리 표시가 필요하다. 전환·정정 규칙은 상세 설계에서 확정한다.

### 6.5. 포함 인원만 갱신

BNOC 소속 부대·선택 기준일에서 인원 식별번호로 대조하여 파일에 있는 정상 행만 입력·갱신한다. 파일에서 빠진 인원의 당일 상태는 보존한다. 오늘 상태가 원래 없는 인원은 미입력으로 남기며 어제 값을 자동 복사하지 않는다. 일일 현황 업로드로 기준 명단을 삭제하거나 소속을 바꾸지 않는다.

예: A=주간, B=휴가, C=출장인 상태에서 A=근무 오프, B=주간인 파일을 올리면 A·B만 바뀌고 C=출장은 유지된다. D의 오늘 값이 없었다면 D는 미입력이다.

미리보기에는 신규·변경·동일·누락·오류를 구분하고 변경 전후 값을 보여준다. 빈 상태값은 삭제 명령으로 간주하지 않는다. 미리보기 후 다른 사용자가 수정한 행은 충돌로 구분하여 최신 값과 다시 비교한다.

야간 근무 업로드도 정상 행 우선 반영 원칙을 적용한다. 기존 근무 식별번호로 수정하고 누락 근무를 삭제하지 않는 방식을 설계 기본안으로 둔다. 신규 근무 재업로드의 중복 식별 방식은 API·업로드 양식 설계에서 명시한다.

### 6.6. 정상 행 우선 반영

- 검증·미리보기 후 적용 시 정상 행만 저장하고 오류 행의 기존 데이터는 유지한다.
- 처리 결과에 적용·변경 없음·검증 오류·충돌·저장 실패를 구분한다. 미적용 행은 행 번호와 이유를 제공하여 수정 후 재업로드할 수 있게 한다.
- 식별번호를 기준으로 재적용하므로 이미 반영된 정상 행이 다시 입력되어도 중복 인원·상태를 만들지 않는다.
- 같은 인원·기준일이 파일에 중복되면 해당 중복 행들을 모두 오류로 구분하고 무관한 정상 행을 처리한다. 먼저 나온 행을 임의로 선택하지 않는다.
- 행 검증 오류와 파일 전체 오류를 구분한다. 읽을 수 없는 파일, 필수 열 누락, 권한 없는 부대 대상 등은 파일 전체 처리를 중단하고 이유를 표시한다.
- 검증 오류 2행을 제외하는 것과 저장 중 장애로 일부만 반영되는 것은 다르다. 저장 결과를 확인해 실제 적용 행만 성공으로 표시하고 실패를 전체 성공으로 보고하지 않는다.

예: 30명 중 식별번호 오류가 2명이면 정상 28명을 먼저 반영하고 오류 2명은 기존 값을 유지한다. 수정한 2명만 다시 올려도 되고, 전체 파일을 다시 올려도 이미 같은 28명은 변경 없음으로 처리한다.

### 6.7. 수용 검증 사례

- 공조: B반 수락만으로 작업 생성·BNOC 갱신, 중복 수락에도 작업은 1건, 다른 부서 작업 수정 거부.
- 처리 흐름: 정비반 조치 완료 후 BNOC 종결, 추가 조치·재작업 UI와 전용 상태 없음.
- 통계: 일·주간 예시 일치, 이월 중복 없음, 16시 기록과 현재 현황 구분.
- 업로드: 포함 정상 행만 변경, 누락·오류 행의 당일 값 보존, 오늘 값이 없으면 미입력.
- 부분 반영: 정상 28명 성공·오류 2명 미적용 표시, 오류 수정 재업로드 시 중복 없음, 읽을 수 없는 파일은 전체 오류.

위는 구현 후 확인할 기준이며 실행한 테스트 결과가 아니다.

## 7. PM 진행 계획

### 역할별 대시보드와 오른쪽 패널

최신 사용자 방향을 반영하여 공통 레이아웃(로고·왼쪽 메뉴·가운데 본문·오른쪽 패널) 안에서 역할별 홈을 제공한다. 동일한 정비 현황 화면에 숫자만 바꾸는 방식으로 제한하지 않는다. 오른쪽에는 지시사항과 해당 역할의 알림을 배치하며, BNOC 접수 대기 확인을 포함한다.

세부 배치 제안: BNOC는 운영현황·정비 캘린더·오늘 근무·정비 수치, 정비부서는 자기 부서 작업·일정·근무, 일반 사용자는 정비 요청 바로가기·본인 요청 목록·본인 일정·관련 근무 안내, 상위 조회자는 허용 부대의 읽기 전용 요약을 제공한다. 공통 대시보드는 메뉴의 첫 항목이며 일반 사용자가 본인 요청 화면을 첫 화면으로 사용한다는 이전 제안은 개인 홈의 요청 바로가기로 대체한다.

오른쪽 패널의 업무 목록은 BNOC 접수·종결 대기, 정비부서 미확인 배정·공조 수신, 일반 사용자 본인 처리 변경을 기본 제안으로 한다. 지시사항은 게시 대상 권한을 따르고 일반 사용자에게 내부 지시를 자동 공개하지 않는다. 부서 작업 알림은 개인별 알림 읽음과 별개다.

한 패널에 모든 항목을 쌓지 않고 짧은 미리보기와 전체 보기를 제공한다. BNOC는 처리 대기를 위에, 지시사항을 아래에 두는 구성을 제안한다. 지시사항 팝업을 기본으로 중복 표시하지 않는다. 미처리 건수와 안 읽은 알림 수를 같은 숫자로 취급하지 않는다.

화면 구현은 아직 시작하지 않았다. BNOC·일반 사용자 두 역할의 시안을 먼저 비교하고 정비부서·조회자로 확장한다. 특기별 운영체계 첫 표시, 일반 사용자 근무 정보 범위, 날씨 연동은 상세 설계 제안이며 접근 권한 확대나 외부 연동 확정이 아니다.

### 요청 입력 자동화·태그·부서 알림 보완

확정사항: 작업 알림은 부서 대상으로 제공한다. 계급·성명·사무실 전화번호는 자동 입력한다. 현재 시연은 가상 계정 정보를 사용해 인트라넷 연동 결과를 모사하며 실제 인트라넷 연동은 이번 범위 밖이다. 프로필 누락값은 임의로 만들어 채우지 않고 안내한다.

제목·태그는 사용자가 가능성을 문의한 항목으로 다음을 설계 제안한다. 구현 완료나 사용자 최종 선택으로 표시하지 않는다.

| 항목 | 제안 |
|---|---|
| 요청 부서 | 계정 소속으로 기본 입력. 임의 다른 부대 요청을 허용하지 않고 대리 요청 여부는 추후 필요 시 검토 |
| 요청 내용 | 첫 줄에 요약, 이후 상세 설명. 별도 제목 입력 없이 제목 미리보기 제공 |
| 제목 | `[요청 부서] 내용 첫 줄`. 긴 첫 줄은 표시 길이를 제한하고 전체 본문은 보존. 제출 시 서버에서도 같은 기준으로 생성 |
| 태그 | 기본 미선택, 사용자가 선택 가능, 미선택 신청도 허용, BNOC가 접수 과정에서 지정·수정 |
| 후보 추천 | 키워드·동의어 기반 후보 표시. ‘모니터’는 모니터, ‘PC·포맷’은 PC, ‘랜선’은 네트워크 후보. 자동 확정·부서 자동 배정으로 연결하지 않음 |
| 분류 범위 | PC·모니터·전화기·네트워크 등 후보 목록을 공통 관리. 다중 태그 허용 여부·최종 목록은 화면 검토에서 결정 |
| 알림 확인 | 부서 구성원이 작업 알림 조회. 한 사람이 알림을 읽었다고 모두의 읽음이나 작업 확인을 자동 변경하지 않음. 실제 작업 확인 주체·시각 기록 |

예: 가상 계정의 요청 부서가 ‘보급대대 유류통제반’이고 내용이 ‘모니터 2대 정비 요청’이면 제목을 ‘[보급대대 유류통제반] 모니터 2대 정비 요청’으로 생성하고 모니터 태그를 추천한다. 사용자가 태그를 선택하지 않으면 미분류 상태로 BNOC에 접수한다. 요청 1건·단일 부서 작업 1건은 그대로다.

키워드 추천은 기술적으로 가능하지만 ‘PC는 정상이고 전화기만 고장’ 같은 문장의 의미를 단순 단어 포함만으로 정확히 판단하지 못한다. 시연의 기본 기능은 수동 선택·BNOC 분류로 완성하고 추천은 그 위에 추가하는 방향을 권장한다. UI에서 추천과 확정 태그를 구분한다. 기획용 제목 생성에는 AI 요약이 필요하지 않다.

### 7.0. 후속 업무 질문 답변 — 확정 기록

이 절은 메뉴 개정 후 받은 다섯 질문의 답변과 사용자 예시를 기록한다. 앞선 기본안을 아래 내용으로 보완한다.

| 항목 | 확정 내용 |
|---|---|
| 요청 단위 | 개인이 작성한 게시글·요청서 1개는 요청 1건. 한 부서가 10대 처리해도 작업 1건. 추가 메모에 수량·범위를 적고 개별 장비별 완료 관리는 도입하지 않는다. 여러 부서 참여 시 기존 부서별 작업 1건 기준 유지 |
| 작업 확인·상태 | 확인과 시작은 별개. 작업 예정·작업 중·보류·완료를 사용하며 애매하거나 대기할 때 보류 사유 기록 |
| 잘못된 배정 | 정비부서가 사유와 함께 BNOC에 재배정 요청, BNOC가 확정. 공조 추가와 구분 |
| 다른 부서 조회 | 정비부서 대시보드는 자기 부서 기본. 같은 대대의 다른 부서 정비 요약 조회 허용, 수정은 자기 작업만. 병력·운영상황·지시사항 권한은 별도 |
| 월간 실적 | 지난달 접수하고 이번 달 완료한 작업은 이번 달 완료 실적에 포함. 이월·신규 배정·완료·잔량 함께 표시. 대시보드 현재 잔량과 정비 현황 선택 기간 실적 구분 |
| 담당 업무 예시 | 네트워크체계팀: 랜선 고장, 모니터 정비 요청, PC 포맷. 사용자 제공 분류를 업무 안내 예시에 사용 |
| 병력 배치 | 부서별 섹션·블록 유지, 각 블록 안 반원을 계급순으로 한 행씩 세로 나열. 주간 / 오프 / 휴가 / 출장 표시, 미입력 유지 |
| 근무자(야간) | 통신일직·작통일직·생활관 근무자 등 구역·직책별로 당직 사관의 계급·성명·전화번호 표시. 대대별 BNOC 등록·취합 유지 |
| 표시 환경 | 약 75인치 TV, 주 사용 브라우저 Edge. 픽셀 해상도·배율·시청 거리·Edge 버전은 미확인 |

추가 메모는 요청 작성 및 작업 상세에 표시하는 단순 텍스트로 설계한다. 예: ‘모니터 10대, 가상 교육장 대상’. 장비별 작업을 자동 생성하지 않는다. 최초 요청 메모와 정비사의 조치내역은 구분한다.

월간 사례: 지난달 미완료 4건을 이월하고 이번 달 신규 2건을 배정하여 이월 중 3건을 완료했다면 이번 달 대상 6건·완료 3건·잔량 3건이다. 기간 내 고유 작업 기준과 16시 보고 보관은 유지한다. 다른 부서로 재배정된 작업의 부서별 실적 귀속은 상세 규칙 결정 대상이며 작업을 복제해 전체 건수를 늘리지 않는다.

병력 표시명 ‘주간’은 기존 ‘주간 근무’, ‘오프’는 기존 ‘근무 오프’와 같은 의미로 통일한다. 업로드 값 대응도 양식에서 명시한다. 계급·성명·전화번호는 기존 가상 자료 원칙에 따라 시연용 가칭과 가상 번호를 사용한다.

현재 업무 흐름·화면 검토를 먼저 보강한다. 물리 DB·API 확정은 대표 시나리오와 입력항목 검토 후 진행한다. 남은 자료는 평가표·필수 시연 항목과 실제 TV 출력 해상도이며 지금 답이 없어도 화면 시나리오 정리는 가능하다.

### 7.1. 2026-09-09 메뉴 개정 반영

사용자 확정 구조는 다음과 같다. 기존의 상위 두 탭 및 정비사의 일반 접수 승인 규칙을 대체한다.

```text
대시보드
정보통신 운영
 ├ 정보통신 운영현황
 └ 정보통신 상황
    ├ CPCON
    └ GPS 전파교란 위기경보단계
부대운영
 ├ 병력 현황
 ├ 근무자(야간)
 └ 지시사항
정비관리
 ├ 정비 요청  — 일반 사용자 신청·본인 내역
 ├ 정비 접수  — BNOC 접수·부서 배정·최종 종결
 ├ 정비 진행  — 부서 작업 확인·진행·완료·공조·일정 통합
 └ 정비 현황  — 월간·날짜·기간별 부서 실적
```

업무 편의 제안은 BNOC의 부대 전체와 정비부서의 자기 부서를 대시보드·정비 현황의 기본 범위로 사용하는 것이다. 대시보드 카드·그래프를 누르면 동일 부대·부서·기간·상태의 목록으로 이동한다. 전체 구조의 첫 메뉴는 대시보드지만 역할별 접근 범위는 서버에서 제한한다. 일반 사용자의 대시보드는 본인 요청 요약을 기본 제안으로 두며 부대 운영정보 권한을 자동 확대하지 않는다.

‘정비 현황’의 부서별 접수는 ‘배정 작업’으로 표시하는 것을 권장한다. 요청 접수 ID와 부서 작업 ID를 섞지 않는다. 상세 작업과 수동 건수는 출처를 분리한다. 기간 중 배정 유입 건수와 전일·전월 이월을 포함한 관리대상 수도 구분한다. 현재 작업 중과 전체 미완료를 같은 ‘진행 중’ 이름으로 혼용하지 않는다.

권장 카드: BNOC는 미배정 요청·미확인 배정·작업 중·보류·조치 완료·종결 대기, 정비부서는 자기 부서 미확인·작업 중·보류·완료·공조 수신·오늘 일정이다. 미확인은 확인 여부, 작업 예정/중/보류/완료는 작업 상태, 종결 대기는 접수 상태이므로 카드 전체를 합산한 총건수를 만들지 않는다. 그래프는 같은 단위인 작업상태별 분포만 비교한다.

### 7.2. 후속 단계

1. 요구사항 분석: 이 문서를 기준으로 영향이 큰 미정 사항을 구체화한다.
2. UX·기술 검토: 역할별 흐름·핵심 와이어프레임과 지정 스택 실행 가능성을 함께 검토한다.
3. UI·구현 명세: 디자인 규칙과 데이터·API 계약을 맞추고 한 사용자 흐름의 수용 기준을 확정한다.
4. 첫 구현: 시연 로그인, 미지정 신청, BNOC 배정, 정비사 완료, BNOC 종결, 두 화면 자동 갱신을 연결한다.
5. 기능 확장: 병력·업로드·야간 근무, 운영상태·상황·지시, 집계·캘린더·전시기 기능을 순차 완성한다.
6. 통합 검증: 권한 분리, 오류·동시 처리·재연결, 시연 순서와 배포 절차를 검증한다.

11월 6일은 고정 제출 목표다. 내부 목표는 10월 말 기능 완료 후 남은 기간을 결함 수정·시연 준비에 사용하는 것으로 제안한다. 주별 일정과 사람별 배정은 가용 시간 및 기술 검토 없이 확정하지 않는다.

Q-01~Q-05와 2026-09-09 메뉴 개정을 반영하고 UX·기술 문서 검토를 완료했다. 산출물은 [UX 명세](design/ux-spec.md), [기술 검토](development/technical-plan.md), [Planner 조율 기록](design-development-review.md)이다. 다음 단계는 대표 업무 시나리오와 화면 입력항목 검토다. 물리 DB·API 확정은 이후 진행한다. 제품 코드는 미구현이며 빌드·화면·DB·동기화 실행 검증은 아직 수행하지 않았다. 남은 세부 결정은 해당 기능의 상세 설계에서 다룬다.
